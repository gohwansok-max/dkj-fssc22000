# 새 사업장(다른 농협) 찍어내기

## 지금 이 스킬이 할 수 있는 것 / 없는 것

**아직 원클릭 자동화가 아니다.** Firebase 프로젝트 생성, GitHub Pages 커스텀
도메인 연결처럼 콘솔에서 사람이 직접 눌러야 하는 단계가 섞여 있다. 이 스킬은
그 과정을 빠뜨리지 않고 순서대로 밟도록 안내하는 것부터 시작한다. 자동화
가능한 부분(파일 검색-치환, 카탈로그 JSON 틀 생성, 번들 재생성 등)은 이 스킬을
쓸 때마다 조금씩 늘려간다 — `docs/NEW_TENANT_HARNESS.md`의 "아직 안 된 일"
항목이 자동화 로드맵이다.

## 절차

1. **`docs/NEW_TENANT_HARNESS.md`를 먼저 읽는다.** 특히 PART 3("`dkj-fssc22000`
   → 새 테넌트 전환 시 반드시 바꿔야 하는 것") 표가 이번 작업의 실제 작업
   목록이다.

2. **사용자에게 확인받을 것** (AskUserQuestion으로 한 번에 묻는다):
   - 새 사업장 정식 명칭 / 약칭 (예: "공덕농협 미곡종합처리장" / "GD")
   - 문서번호 프리픽스를 새로 만들지, 당분간 `DKJ-`를 유지할지
     (PART 3 참고 — 프리픽스를 바꾸면 서식 74종 파일명·코드를 전부 리네임하는
     큰 작업이다. 처음엔 유지하고 회사명·로고만 바꾸는 것도 현실적 선택지라고
     알려준다)
   - 새 Firebase 프로젝트를 사용자가 이미 만들어뒀는지, 아니면 지금부터 안내가
     필요한지
   - 배포 저장소를 이 저장소에서 새로 fork할지, 다른 방식(예: 템플릿 저장소
     사용)을 원하는지

3. **fork/새 저장소 준비** — 사용자가 원하면 GitHub 저장소를 새로 만들고
   (`mcp__github__create_repository` 또는 `fork_repository`) 이 저장소의 코드를
   그대로 시작점으로 올린다.

4. **PART 3 표를 순서대로 처리** — 검색-치환이 필요한 항목(회사명, 브랜드 자산,
   `4343` 등 하드코딩된 사번)은 `Grep`으로 전체 위치를 다시 확인한 뒤 일괄
   치환한다. `data/*.json` 14개는 새 사업장 내용으로 다시 채운다(빈 틀만 만들고
   내용은 사용자에게 받는 것도 방법).

5. **PART 1(새 사업장 배포 전 필수 체크리스트)을 그대로 따라간다** — 특히
   `sync_meta/schemaVersion` 직접 확인, `database.rules.json` Rules 탭 Publish는
   절대 건너뛰지 않는다. 이 두 개를 놓쳐서 동김제에서 며칠이 날아갔다.

6. **완료 후**: 카탈로그 재빌드(`build-catalog-bundles.py`), 서비스워커
   프리캐시 재생성(`build-sw-precache.py`), 실기기(PC+폰) 양쪽에서 로그인 →
   저장 → 상대 기기 동기화 확인까지 마쳐야 "완료"로 본다.

## 이 스킬 자체를 키워나가는 법

새 사업장을 하나 찍어낼 때마다 겪는 새로운 문제(동김제 때와 다른 종류의
버그·삽질)는 `docs/NEW_TENANT_HARNESS.md`에 PART 2 형식(증상→원인→고침→교훈)으로
추가하고, 자동화할 수 있게 된 단계는 이 파일의 "절차"를 갱신한다. 이 스킬과
하네스 문서는 정본을 `dkj-fssc22000`에 두고, 다음 사업장 저장소들은 필요할 때
이 문서를 참고만 하면 된다(각자 fork에 복사해서 따로 발전시키지 않는다 — 그러면
다시 흩어진다).
