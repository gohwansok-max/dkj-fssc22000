# 새 사업장(다른 농협) 찍어내기

## 진짜 목표부터 — 브랜딩이 아니라 문서 매핑이 핵심

목표는 "사업장 하나당 2일". 시간이 실제로 드는 곳은 순서대로:

1. **오프라인 문서를 받아서 서식(기록양식)으로 옮기는 판단 작업** — 압도적으로
   오래 걸리고, 사람이 아니라 이 세션(Claude)이 직접 해야 하는 부분. 여기가
   진짜 병목이다.
2. 카탈로그 JSON 4종에 새 서식 등록 — 기계적이지만 아직 스크립트 없음(수작업).
3. 브랜딩(회사명·사번) 치환 — `scripts/new-tenant-rename.py`로 이미 자동화됨.
4. Firebase 신규 프로젝트·배포·검증 — 체크리스트로 정리돼 있음, 콘솔 클릭은
   사람이 직접 해야 함.

**그래서 Day 1은 문서 매핑에 몰아쓰고, Day 2는 브랜딩·Firebase·배포·실기기
검증에 쓰는 배분을 기본으로 잡는다.** `docs/NEW_TENANT_HARNESS.md`를 먼저
읽는다 — 이 스킬은 그 문서의 실행 절차이고, PART 0가 이 목표를, PART 5가
문서 매핑 방법을 자세히 다룬다.

## Day 1 — 오프라인 문서 → 서식

1. 사용자에게서 새 사업장의 오프라인 문서(HACCP 계획서·SOP·점검표 등, Word/
   PDF/한글/이미지 무엇이든)를 받는다. 한 번에 다 못 받으면 우선순위 높은
   것부터(매일 작성하는 CCP·품질 기록류) 받는다.
2. 문서마다 `docs/NEW_TENANT_HARNESS.md` PART 5-1의 표로 어느 엔진
   (`fr-form`/`ledger-form`/`matrix-form`/`ox-form`/`report-form`, 또는 예외적으로
   전용 스크립트)에 맞는지 정한다. 애매하면 동김제 74종 중 비슷한 서식의 스펙
   JSON을 찾아 복사해서 시작하는 게 가장 빠르다.
3. PART 5-2의 7단계(스펙 JSON → HTML 껍데기 → record-catalog.json →
   console-forms.json → mdr-catalog.json → print-templates → 번들 재생성)를
   서식마다 반복한다. **문서번호·Rev·작성자/검토자/승인자·한계기준 이탈 시
   시정조치 필수화 같은 심사 필수 요소를 빠뜨리지 않는다**(PART 5-3, 이 저장소는
   `quality-record-app-rules` 규칙이 적용되는 A등급 시스템이다).
4. 서식이 다 옮겨지면 실제 브라우저(`python -m http.server` 로컬 서버)로 하나씩
   열어서 저장·기록보관함 반영까지 확인한다 — 코드만 보고 됐다고 판단하지 않는다
   (PART 4의 교훈).

## Day 2 — 브랜딩 · Firebase · 배포

1. **사용자에게 확인받을 것** (AskUserQuestion으로 한 번에 묻는다):
   - 새 사업장 정식 명칭 / 조합명 / 약칭 (예: "부안농협 미곡종합처리장" /
     "부안농협" / "부안") — `scripts/new-tenant-rename.py`의 `--org-full`/
     `--org-mid`/`--org-short`에 그대로 들어간다
   - `index.html` 헤더의 시설유형 표기("산지유통센터")를 그대로 쓸지, 다른
     표기("미곡종합처리장" 등)로 바꿀지 — 스크립트가 자동으로 못 바꾸는
     부분이라 별도로 안내
   - 새 시스템 관리자 사번(4자리)
   - 문서번호 프리픽스(`DKJ-`)를 새로 만들지, 당분간 유지할지 — 바꾸면 서식
     74종+새로 옮긴 서식까지 파일명·코드를 전부 리네임하는 큰 작업이니, 처음엔
     유지하고 브랜딩만 바꾸는 것도 현실적 선택지라고 알려준다
   - 새 Firebase 프로젝트를 이미 만들어뒀는지, 지금부터 안내가 필요한지
   - 배포 저장소를 이 저장소에서 새로 fork할지

2. **fork/새 저장소 준비** — 사용자가 원하면 GitHub 저장소를 새로 만들고
   (`mcp__github__create_repository` 또는 `fork_repository`) 이 저장소(Day 1에서
   서식을 이미 옮긴 상태)를 시작점으로 올린다.

3. **브랜딩 일괄 치환**:
   ```
   python scripts/new-tenant-rename.py --org-full "<정식명칭>" \
       --org-mid "<조합명>" --org-short "<약칭>" --admin-emp-id <사번>
   ```
   먼저 `--apply` 없이 돌려 미리보기를 확인하고, 이상 없으면 `--apply`를 붙여
   다시 실행한다. 실행 후 안내되는 후속 작업(index.html 시설유형 표기,
   `build-catalog-bundles.py`, `build-sw-precache.py`)을 빠뜨리지 않는다.

4. **PART 1(새 사업장 배포 전 필수 체크리스트)을 그대로 따라간다** — 특히
   `sync_meta/schemaVersion` 직접 확인, `database.rules.json` Rules 탭 Publish는
   절대 건너뛰지 않는다. 이 두 개를 놓쳐서 동김제에서 며칠이 날아갔다.

5. **완료 후**: 실기기(PC+폰) 양쪽에서 로그인 → 저장 → 상대 기기 동기화
   확인까지 마쳐야 "완료"로 본다.

## 이 스킬 자체를 키워나가는 법

새 사업장을 하나 찍어낼 때마다 겪는 새로운 문제는 `docs/NEW_TENANT_HARNESS.md`에
PART 2 형식(증상→원인→고침→교훈)으로 추가하고, 자동화할 수 있게 된 단계는 이
파일과 PART 3 "아직 안 된 일"을 갱신한다. 다음 자동화 1순위는 카탈로그 4종 등록
스크립트다(PART 3 참고) — 이게 되면 Day 1의 반복 작업이 크게 줄어든다. 이 스킬과
하네스 문서는 정본을 `dkj-fssc22000`에 두고, 다음 사업장 저장소들은 필요할 때
이 문서를 참고만 하면 된다(각자 fork에 복사해서 따로 발전시키지 않는다 — 그러면
다시 흩어진다).
